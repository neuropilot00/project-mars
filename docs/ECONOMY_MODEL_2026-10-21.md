# Occupy Mars 경제 모델과 재현 근거 — 2026-10-21

이 작업은 DB/지갑에 접속하지 않는 실행 가능한 경제 모델과 회귀 검증을 완성한다. 런타임 서비스, 설정, 실제 잔액을 변경하지 않는다. 경제 지표는 명시한 행동 가정을 실행한 결과이며 수요·유지율·수익성 예측이 아니다. GP/PP에 현금 청구권을 추가하지 않고, 영토·함선은 게임 내부 소유권으로 유지한다.

## 실행과 산출물

저장소 루트에서 Node의 내장 모듈만으로 실행한다. npm 설치, `.env`, DB, RPC, 계정, 키가 필요 없다.

```sh
node --test server/tests/economy-scenario-simulation.test.js
node server/tools/economy_scenario_simulation.js --seed 20261021 --out ../../outputs/evidence/economy-followup-20261021
```

- `economy-scenarios.json`: 소스 SHA-256, 정책/가정, 시나리오별 발행·실제 소각·이전·재고·가격·거래·분포·준비금·고객 부채·미확정 출금.
- `economy-events.jsonl`: 가상 시간과 정책 버전이 포함된 실제 실행 순서의 사건. 시나리오별 `scenarioSequence`는 게임/수탁 원장을 가로질러 증가한다. 각 원장 내부 `sequence`도 보존한다.
- `economy-scenarios.md`, `economy-scenarios.html`: 요약 및 선택 가능한 상세 대시보드. HTML은 외부 라이브러리/네트워크 없이 작성된다.
- `economy-simulation-tests.tap`, `economy-replay-check.json`: 집중 검증과 바이트 단위 재현 결과.

고정 seed `20261021`, 가상 기준일 `2026-10-21T00:00:00Z`, 정책 버전 `occupy-authored-seeds-2026-10-21-v1`을 사용한다. 현재 시각·`Math.random()`·외부 DB 값은 입력으로 쓰지 않는다. 소스가 바뀌면 입력 코드의 해시가 달라지므로 같은 정책/코드를 비교해야 한다. 프로그램 API `runScenario({ seed, overrides, policyOverrides })`로 행동 가정과 명시적 정책 민감도를 재사용할 수 있다.

## 원장과 불변식

`Ledger.post`는 사건을 임시 검증한 뒤 한 번에 반영한다. 자산별 차변/대변 합0, 허용된 발행자/소각자, 소유자만 가능한 차감, 음수 잔액 금지, 고유 사건 ID를 매 사건 검증한다. 실패한 batch는 부분 반영하지 않는다. 일반 actor는 타인 자산 차감이나 시스템 발행을 할 수 없다. 모델의 `engine`, `verified_funding` 같은 actor는 가상 검증 오라클이며 실제 JWT/서명 검증을 대체하지 않는다.

각 자산에 대해 `발행 - 실제 소각 = 모든 보유·보관·재무 계정 잔액`이 성립한다. GP/PP, 비환불 접근 크레딧, 광물 종류, 아이템, 함선, 영토를 서로 다른 자산으로 둔다. 시장 매출은 구매자에서 판매자로 이동하며 새 발행이 아니다. 추천·배당·길드·경매 미배분 수수료 계정에 남은 돈은 소각이 아니다. 경매 probe의 미배분 플랫폼 수수료는 보수적으로 재무 계정에 둔다. 실제 경매의 전체 추천 지급 정책을 이 모델이 보증하지 않는다.

건조의 내재 재료, 잔해 재고, 운송/창고는 지갑의 가용 재료와 구분한다. 순환 중 같은 재료를 여러 계정에 복제하지 않는다. 실제 코드에서는 건조 재료가 소비되지만 이후 해체를 위한 출처를 모델이 명시적으로 보관하는 회계 표현이다. 전쟁에서는 원료를 파괴하고, 실제 잔해 수식에 따른 별도 파생 자원을 생성한다. 파생 자원 발행과 수령 이전을 분리해 숨겨진 발행을 없앤다.

## 현금성 자산은 별도 가상 스트레스 원장

USDC, USDT, USDG를 자산별로 독립시켜 실행한다. USDG 지원은 **이 모델의 가상 자산 registry**이며, 체인/발행사/계약/지갑/실제 입출금 지원을 구현했다는 뜻이 아니다. microtoken은 회계 단위이며 특정 체인의 token decimals를 검증했다는 뜻도 아니다. GP/PP를 어느 stablecoin으로도 자동 환매하는 메서드는 없다.

- 최종 자금 확인 예치: 준비금과 고객 부채를 같은 액수만큼 늘린다. 예치금은 사업 매출이 아니다.
- 가상 유료 구매: 예약을 제외한 고객 가용 청구권과 가용 현금이 모두 있어야 한다. 지불한 만큼 부채·고객 준비금을 줄이고 별도 사업 매출을 늘린다. 별도의 비환불 접근 크레딧을 발행한다. GP/PP나 고객 환매 청구권으로 혼합하지 않는다.
- 출금 요청: 고객 청구권과 현금을 예약한다. 요청/timeout 자체로 부채를 지우지 않는다. timeout은 unknown이며 lock을 유지한다.
- 확인된 정산: 해당 예약만 원자적으로 해제하면서 실제 지급액만큼 부채·준비금을 감소시킨다. 검증된 실패만 예약 해제한다. 재정산/위조 정산을 거부한다.
- 각 사건: 고객별 `청구권>=예약`, 자산별 `유동 현금>=예약`, 모든 가용 잔액>=0, 예치/지급/매출/손실 회계 일치를 검사한다. 실패한 정산/소비/정책 밖 변경은 이벤트·잔액·상태를 함께 롤백한다.
- 미확정 자금/reorg: 관찰만으로 청구권을 만들지 않는다. 검증된 최종 확인만 자금 확정이며 reorg된 미확정 이벤트는 청구권0. 확인되지 않은 자금을 출금에 사용할 수 없다.
- 유동성 부족과 지급불능은 다르다. locked reserve는 고객 부채를 여전히 뒷받침하지만 당장 지급할 수 없다. 실제 가상 손실로 준비금<청구권이면 insolvency를 표시하고 지급을 거부한다. 매출이나 GP 발행으로 부족분을 감추지 않는다.

회귀 테스트에는 발견된 `100확정→80출금예약→timeout unknown→30구매` 반례가 포함되어 있다. 이제30구매와30현금잠금은 상태 변경 없이 거부된다. 남은20구매 후80출금의 검증된 정산은 가능하고 최종 부채·준비금은0이다.

시나리오 결과에는 GP/PP 발행·실제 소각과 source, 모든 자원/창고/내재 재료, 거래별 가격·수량·주체, 인간/NPC 거래, VWAP(철만), 주문 미체결, 필수 수리 재료 부재, 철 거래량/평균 가용 재고, 시작·종료 집중도, 가상 봇 점유율이 나온다. 별도 경매 probe는 소유 자산 보관→실제 자금 있는 입찰→이전 입찰 환불→성공 정산과 무입찰 만료 반환, 자기 입찰/자금 부족/중복 정산 거부를 실행한다. 실제 SQL 동시성 검증은 별도 서비스 테스트의 몫이다.

## 행동 가정과 해석 범위

실제 관측치가 없는 확률/수요/가격은 `ASSUMPTIONS`와 각 결과 `parameters`에 노출했다. 초기200GP·자원10/5/3·일반 함선·영토1개는 합성 기존 재산이며 실제 신규 지급 정책이 아니다. PP 초기값0이며 출석/수확에서 PP를 새로 만들지 않는다. 하루 신규 유입을 유료 구매나 매출로 연결하지 않는다. 가상 현금 스트레스 인원은 처음40명으로 고정한다.

접속한 날의 출석은 연속 streak를 유지한다고 단순화한다. 보상 cycle reset의 첫날 변형만 소스처럼 seed 난수를 사용한다. 미션은 세 종류를 유효하게 완료했다는 확률 가정이며 매 활동에 무료 보상을 중복 지급하지 않는다. 수확은 multiplier/cap 후0.1PP 상당1GP라고 가정한다. 광물 드롭은 DB의 실제 `sector_resource_rates`를 조회하지 않는 확률 proxy다. 실제 캡/배율/미션 분포를 완전히 복제하는 모델이 아니다.

대표 채굴 capacity와 HP/수리 모델은 집계 proxy이다. 특히 봇 capacity20에 도달하는 구매비·함선 구성·성장 시간은 추정하지 않는다. 가정한 봇의 GP 점유율을 실제 공격 성공률/무위험 수익으로 해석하면 안 된다. 전쟁은 실제 AI·전술·품질 승률을 예측하지 않으며, 초기 함선은 원래 무료 starter grant가 아닌 가상 기존 일반 소유 함선이다.

시장 인간 철10개 묶음 시작가는 NPC 참조6GP이고 일별 체결수에 따라±1% 변하는 **가상 호가 규칙**이다. 실제 수요곡선·탄력성·가격 예측이 아니다. 거래가 가능한 자금과 자원을 가진 상대가 있어야 한다. 미체결 주문의 장기 보관·재등록·등록 취소 수수료는 일별 거래 proxy에 포함하지 않는다. NPC는 하루4번 등록/판매 시도 proxy로 실행하며 실제10분 scheduler·활성 listing 상한·동적 등록료·동시 등록 순서를 복제하지 않는다. 새 NPC 최초 성공 등록을 가정해 seed를 반영하고, 매매 실패와 무관하게 이후에는 재보충하지 않는다. 실제 원자성은 NPC 서비스 테스트로 검증한다.

경매 probe의 수수료 재무 계정은 미배분액을 소각으로 잘못 세지 않기 위한 보수적 표현이다. 실제 경매 추천·사후 side effect는 해당 서비스 테스트/정책과 별도로 확인해야 한다. 합성 주체만 사용하므로 실거래의 공통 소유·조작 탐지는 검증하지 않는다. self trade/입찰 배제 수와 NPC 거래를 구분하고 조작 제외 실제 시장 volume을 추정하지 않는다.

## 결정이 더 필요한 운영 정책

1. 운영용 정책 manifest와 유효 설정의 승인/버전/발효 시점, 누락·중복 설정을 어떻게 관리할지.
2. 명시적 채굴 cap0을 허용할지와 누가 승인할지. 봇/다중 계정/공통 소유 지갑의 정의·탐지·제재 정책. 모델이 새 수치 제한을 운영에 적용하지 않는다.
3. NPC 새 identity의 생성 권한/전체 인구 상한/재고 획득 경로. 현재 보장은 **identity별 한 번**이며 새 NPC 인구가 무한 증가하면 전체 seed도 증가할 수 있다.
4. 추천·배당·길드·경매 플랫폼 수수료의 동시 배분 예산과 실제 귀속. 할인/관세를 합친 뒤 원 수수료 이상 분배하면 안 된다.
5. 미션15GP와 작은 거래 비용(예: 등록5GP+판매0.3GP)의 관계. 보조금이 비용보다 커도 일일 배정/횟수/실제 행동 검증 때문에 무한 수익 루프가 입증되는 것은 아니다. 실제 최저 비용 행동과 공통 소유 거래를 함께 확인할 필요가 있다.
6. 현금성 서비스는 체인/자산별 최종성·reorg·보류·RPC timeout·재정산·유동/총준비금·환불 계약을 따로 확정해야 한다. 모델의 hypothetical USDG가 실서비스 승인/구현을 뜻하지 않는다.

## 검증 결과와 한계

집중 테스트는 정수 금액, 원장 위조/자금 부족/중복/부분 변경 거부, GP/PP 분리, 수수료 원금 내 배분, 환불, 건조 보관, 수리 광물 구분, 자산별 수탁, timeout 예약 보존, 원자적 정산, reorg, 정책 버전, 고정 seed 재현 및 전체 시나리오 보존식을 검사한다. 결과와 정확한 해시는 같은 evidence 폴더에 저장한다.

이 결과는 로컬 모델 개발 완료 근거이다. 서비스 DB/API 동시성, 실체인·실지갑·결제·배포·리텐션의 완료를 대신하지 않는다. HTML 생성은 확인했지만 `file://` 브라우저 미리보기는 브라우저 URL 정책에 의해 거부되어 화면 렌더/상호작용은 검증하지 않았다. 같은 목적의 우회 경로는 시도하지 않았다.
