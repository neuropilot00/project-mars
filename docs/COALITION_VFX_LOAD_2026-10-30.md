# 600척 포격 표현 및 다중 연결 검증 — 2026-10-30

## 원인과 변경

엔진은 5틱마다 전송하는 프레임에 최대 128개 판정 이벤트만 넣고 초과 시 오래된 이벤트부터 버렸다. 함대 순회 순서 때문에 양측 표시가 치우칠 수 있었으며 실제 피해·격침·보상은 이 제한과 별개였다. 클라이언트도 128개 표시 제한과 이벤트별 함선 선형 검색을 사용했다.

128개 개별 이벤트는 유지하고 초과한 실제 서버 판정을 진영·무기별 건수와 실제 좌표의 대표 궤적 최대 두 개로 집계한다. 우선순위가 높은 격침은 개별 표시를 보존하며 클라이언트는 명령 피해를 재계산하지 않는다. 광역 필살기는 대상별 판정이므로 집계 건수를 독립 탄환 수로 해석하지 않는다. 포격 묶음은 시간차와 제한된 지속시간으로 표현하며 화면 효과와 폭발 수에 상한을 둔다. 함선 조회는 ID Map으로 바꿨다.

희소 저장 리플레이에서 줄어든 프레임의 포격 집계는 다음 보존 프레임에 합친다. 탐색 시 이전 구간 이펙트를 반복하지 않는다. 600척 전체 시뮬레이션은 개별 151,168건+집계 1,144,640건=1,295,808건이었고 승패·통계·게임 이벤트 해시는 기준과 일치했다. 최종 저장 replay는 75프레임, 7,143,935 bytes로 8MiB 예산 아래에 있었다. 저장된 효과는 해당 보존 프레임에서 묶여 표현되며 모든 판정을 개별 선으로 그리지는 않는다.

지원 브라우저는 WebSocket `gzip-v1`을 선택해 서버에서 프레임당 한 번 압축한 메시지를 받는다. 미지원·구형 클라이언트는 기존 JSON을 유지한다. 해독 길이·CRC·전투 ID를 검증하고 오류/지연 시 비압축 재연결한다. 기기가 수신 처리를 따라가지 못하면 오래된 시각 프레임을 건너뛰고 최신 상태 및 제어 메시지를 우선한다. 따라서 극단적 클라이언트 과부하에서는 일부 포격 연출이 여전히 표시되지 않을 수 있다.

실시간 틱은 처리 시간을 목표 틱 주기에서 차감하고 과부하 때 이벤트 루프에 양보한다. 밀린 틱을 한꺼번에 따라잡지 않는다. 같은 틱에 적용한 명령의 결과는 같지만 같은 벽시각에 도착한 명령의 적용 틱은 달라질 수 있다.

서로 다른 WS 인스턴스에서도 사전계산 전투의 관전자를 감지하고 Redis로 프레임을 중계한다. 관전자가 없는 전투는 payload를 발행하지 않고 관전자 확인 요청은 묶는다. Redis 단절 시 로컬 전달은 유지하지만 다른 인스턴스가 놓친 프레임은 소급 재전송하지 않는다.
