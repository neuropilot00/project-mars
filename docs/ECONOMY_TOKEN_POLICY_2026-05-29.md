# OCCUPY MARS — 토큰·현금화 경제 정책 (2026-05-29)

> 출처: 적대 토론 워크플로(옹호=P2E 수익 / 설계=토크노믹스 / 규제=규제현실) → 중립 심판 단일 권고.
> 상태: **정책 확정 + W단계 구현 진행 중**. M단계(법인구조·캡드토큰)는 보류.

---

## 0. 한줄 결론

**PP→USDT는 "1:1 페그"가 아니라 코드에 이미 있는 담보-룸(room = 담보 USDT − Σusdt_balance) 내 재량 환매로 살린다. GP·PP는 온체인에 올리지 않고 오프체인 크레딧으로 둔다. 토큰화는 보류.**

세 전문가 수렴점: (a) 무캡 GP 토큰화는 수학적 자살(균형가 0 수렴), (b) 환매는 담보 한도 내로 묶고, (c) "1:1 peg" 문구는 프리런칭 무비용 시점에 영구 차단.

---

## 1. 사장 질문 직답

### Q1. "PP 못 바꾸면 과금요소가 없잖아?"
→ **현금화를 없애지 않는다. "한도"만 건다.** 유저 화면엔 여전히 `PP → USDT 출금` 버튼이 있다. 달라지는 건 운영자가 지는 부채뿐(무한 → 신규입금 연동 상한). **과금 훅 100% 유지, 부채만 통제.** 포기하는 건 "1:1" 광고 문구 하나 — 매력 손실이 아니라 법적 시한폭탄 제거.

### Q2. "토큰 만들려면 GP를 토큰화해야 맞지?"
→ **아니다. GP 토큰화가 가장 위험한 선택.** GP는 무캡 발행(로그인·전투·미션·가챠·원정 5 faucet). AMM 상장 시 발행>소각인 한 가격이 수학적으로 0 수렴(균형가 부재) → 5 faucet이 매도탭이 되어 LP 담보 고갈. GP는 페그가 없어 "현금화 신뢰"도 못 만든다. **GP 토큰화는 오히려 과금 훅을 죽인다.**

## 2. 축1 — 현금화/페그: "담보-룸 소프트 환매"

| 레버 | 설정값 | 구현 위치 |
|---|---|---|
| 환매 형태 | room(담보 USDT − Σusdt_balance) 한도 내 best-effort | `treasury.lockRoom` (기구현, mig 230) |
| 환매 대상 PP | **입금 연동 잔액(redeemable_pp)만**. 채굴·가챠 PP는 GP로만 전환(USDT 직행 차단) | `users.redeemable_pp` (mig 271) |
| 주간 환매 한도 | max(절대바닥, **신규 입금의 30%**) | `treasury.checkRedemptionLimits` |
| 유저 일일 한도 | 설정값(USDT) | 동일 헬퍼 |
| 환매 수수료 | swap_fee_percent (sink, 소각/퀘스트풀) | 기구현 |
| 정산 딜레이 | withdrawal_cooldown_hours (24~72h) + KYC | 기구현(cooldown), KYC=운영 |
| 환율 표기 | "운영 환율(변경 가능)" — "1:1/peg/투자수익" 단어 금지 | index.html i18n |

**핵심 혁신 = 채굴 PP의 USDT 직행 차단.** 봇이 일0.3cap을 멀티계정으로 긁어 USDT로 탈출하는 차익 구멍을 닫는다. "순진한 1:1"(무한부채)도 "완전 자유변동"(매수 sink 0→붕괴)도 아닌 중간값.

> **솔벤시 하드 가드는 여전히 room(담보) 가드다.** redeemable_pp 게이팅은 그 위에 얹는 봇-차익 차단 레이어이며, 담보 불변식을 약화시키지 않는다(redeemable 로직에 빈틈이 있어도 room 가드가 미담보 USDT 발행을 막는다).

## 3. 축2 — 토큰화 대상: 셋 다 지금은 안 함

- **GP 토큰화 = 절대 금지.** 무캡 5-faucet → AMM 상장 시 가격 P→0. 사장 직감이 가장 위험.
- **PP 토큰화 = 보류.** 이미 "환매 기대"가 붙어 온체인화 즉시 가상자산이용자보호법 적용(트래블룰·예치금분리·해킹배상). 오프체인 크레딧 유지.
- **신규 캡드 토큰 = 보류(폐기 아님).** 법인소재지·타겟시장·규제자문 확정 후의 "성장 옵션". 발행 시에도 거버넌스/시즌패스/영토 프리미엄 등 **소비 유틸리티 한정**, 배당·되사주기 효용 금지(증권성 트리거).

## 5. 설정 키 (mig 271 신규)

| 키 | 기본 | 용도 |
|---|---|---|
| `redeemable_pp_gating_enabled` | `true` | 환매를 redeemable_pp(입금연동)로 제한 on/off |
| `redemption_weekly_cap_enabled` | `false` | 주간 환매 한도 게이트(런칭 후 입금 흐름 확인 뒤 on — 입금 0일 때 30%=0 잠금 footgun 회피) |
| `redemption_weekly_cap_pct` | `30` | 주간 신규입금 대비 환매 허용 % |
| `redemption_weekly_cap_floor_usdt` | `100` | 주간 환매 절대 바닥(잠금 방지) |
| `redemption_daily_limit_usdt` | `0` | 유저별 일일 환매 한도(0=무제한) |

> **`redeemable_pp_gating_enabled` 기본 true 안전 근거**: 프리런칭(USDT 0, 입금 0)이라 기존 dev 유저의 PP는 전부 채굴/가챠(=비환매). redeemable_pp 백필=0이며 room도 0이라, 게이팅을 켜도 dev에서 환매 동작 변화 없음(어차피 room=0으로 막힘). 런칭 후 입금이 redeemable_pp를 적립하면서 정상 작동.

---

## 6. 가장 큰 잔여 리스크

실측 환매율이 가정(활성 10~25%)을 넘으면 담보풀이 마르고, 그때 한도를 조이면 "사실상 페그 파기"로 신뢰가 무너지는 단방향 리스크(뱅크런). `redemption_weekly_cap_pct`(30%)가 1차 방어선이지만 입금 정체 시 개별 유저는 "내 돈 못 뺀다"고 느낀다.

**완화책**: room/환매율을 공개 대시보드(W6-10)로 투명 공개해 "담보 한도 내 재량"을 처음부터 사실로 학습. **환매율 실측이 런칭 후 최우선 관측 지표.**
