# Crafting card localization and string recipe IDs

The actual recipe API returns BIGSERIAL IDs as strings. The card emitted `attemptCraft(1)`, while the handler matched strictly against `r.id`, so the click silently returned. Matching canonical string IDs now finds the actual recipe; the existing POST sends its original `recipe.id`. The route already parses this ID with `parseInt(recipeId, 10)`. Authentication, recipe availability, ingredient checks, GP handling, success rates and refund policy are unchanged.

Cards now render their localized action immediately with seven inline arguments. The old dynamic `data-i18n="craft_btn"` is removed because the existing SEA key values are themselves English and could overwrite the localized label. Category badges reuse existing inventory/crafting keys. Ingredients reuse `_itemName` and `syResourceName`, preserving existing unknown-code/name fallback and escaping. The existing mineral helper provides Korean names and English fallback for other languages; no new mineral catalog is introduced. Art, layout and actions are preserved.

Validation: `node --check assets/economy-inventory.js`; `node --test tests/crafting-ui.test.js tests/crafting-card-localization.test.js` — 18/18 passed. Tests execute actual renderer/handler source, real seven-language dictionaries and the existing mineral helper. They cover string-ID rendered click to confirmation, decline with zero requests, acceptance with the original selected ID, ingredient rejection, server GP error, translated cards and unknown fallbacks. No live network, database or crafting mutation was used. Parent performs actual mobile browser verification.

## Confirmed balance refresh and shop cost notice

The old post-craft `refreshBalance`/`updateBalanceDisplays` calls did not exist in the actual product. Confirmed outcomes now await the real `refreshEmailBalances(true)`, then repaint `_updateBaseShopBalances()` and reload recipes. The profile hook accepts an optional force flag; its existing callers keep cached behavior. Forced reads wait for any earlier same-token in-flight read and then fetch fresh `/api/auth/me`, preventing pre-craft balances from satisfying a post-craft refresh. Wallet and token checks prevent delayed responses or continuations from repainting another session. No displayed balance is calculated from the cost or outcome locally.

A notice appears in the card and confirmation only when the exact output item ID matches an active loaded shop item with a finite positive `price_gp`, the output quantity is a positive integer and that quantity's shop GP total is lower than the recipe's GP cost. The actual existing shop renderer uses `price_gp`, not `gp_price`. The seven-language notice states the known shop total and reminds the player to check their crafting mission. Missing IDs/prices/quantities, invalid values and equal/higher totals produce no notice. Prices, ingredients, mission conditions and success/refund policies are unchanged.

Updated validation: `node --test tests/crafting-ui.test.js tests/crafting-card-localization.test.js` — 30/30 passed. The fixture now executes actual profile `fetchAuthMe`, `refreshEmailBalances`, `_applyAuthMeBalances`, actual GP display and base-shop balance renderers; nonexistent balance-hook stubs were removed. Cached 85 GP is replaced by confirmed 35 GP in wallet/profile/base nodes, old in-flight reads are followed by a fresh read, wallet/token switches discard responses, and real card/confirmation source is checked in all seven languages. No real API or economic action was executed by these tests; actual mobile verification remains with the parent.
