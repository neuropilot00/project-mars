# OCCUPY MARS — Commercial Open Readiness Plan

> 재정리일: 2026-05-14  
> 기준 브랜치: `main`  
> 목적: "기능 많은 테스트 빌드"를 "상업 오픈 가능한 운영 빌드"로 전환하기 위한 **실행순서 / 오픈 blocker / 출시 게이트**를 현실적으로 재정렬한다.

---

## 1. 이번 재정리의 결론

지금 `occupy-mars`의 핵심 문제는 "기능이 부족해서 출시를 못 하는 상태"가 아니다.  
오히려 아래 4가지 때문에 **상업 오픈 판단이 아직 이르다.**

1. **운영 진입 방식이 아직 테스트용이다.**
   - `start-test.sh`가 로컬 서버 + Cloudflare Tunnel + 관리자 비밀번호 `admin1234` 노출 흐름을 그대로 제공한다.
   - 이건 지인 테스트에는 빠르지만, 상업 운영 표준으로는 부적합하다.

2. **보안 감사는 많이 진행됐지만, 회귀 제어 체계가 약하다.**
   - `AUDIT_FINDINGS.md` / `CHANGELOG.md` 기준 2026-05-07~2026-05-14 사이 치명/고위험 수정이 매우 많이 누적됐다.
   - 최신 감사 요약상 미수정 잔여 항목은 없지만, 최근에도 `admin.html`, `campaign-editor` 회귀가 다시 터졌다.
   - 즉, 지금의 진짜 리스크는 "미발견 치명 버그"보다 **보안 수정 이후의 기능 회귀**다.

3. **출시 반복검증 세트가 없다.**
   - `server/package.json` 기준 스크립트는 `start`, `dev`만 있고 테스트 스크립트가 없다.
   - 상업 오픈 전마다 돌릴 자동/반자동 스모크 팩이 없는 상태다.

4. **운영 문서/복구 문서/배포 표준이 부족하다.**
   - 저장소 탐색 기준 별도 health/deploy/runbook/backup 문서가 바로 확인되지 않았다.
   - 오픈 자체보다, **문제 발생 시 어떻게 감지하고 되돌릴지**가 더 취약하다.

**따라서 지금 필요한 것은 대규모 리팩터링이 아니라:**
- 테스트용 공개 경로 제거
- 회귀 방지용 릴리즈 게이트 구축
- 관리자/결제/경제/영토 핵심 동선의 반복 검증 확보
- 운영 런북/백업/롤백 기준 확정

이다.

## 2. 현재 기준 사실 요약

### 이미 좋은 점
- 최근 감사 흐름상 **핵심 서비스/주요 라우트/프론트 핵심 함수**까지 폭넓은 점검이 진행됐다.
- `AUDIT_FINDINGS.md` 최신 요약 기준:
  - 다수의 CRITICAL / HIGH / MEDIUM 이슈가 수정되었고
  - "미수정 잔여 항목 없음"으로 정리돼 있다.
- 즉, 코드베이스는 "방치된 초기 상태"가 아니라 **빠르게 수습 중인 상태**다.

### 아직 상업 오픈 blocker가 되는 점
- `start-test.sh`
  - Cloudflare Tunnel 즉시 공개
  - 관리자 비밀번호 `admin1234` 노출
  - 운영/테스트 경계 없음
- 최근 회귀 사례
  - `admin.html`의 `window.ADMIN_SECRET` 동기화 누락
  - `campaign-editor` admin auth 회귀
- 테스트 체계 부재
  - `server/package.json`에 `test` 스크립트 없음
- 운영 표준 부재
  - health check / 백업 / 복구 / 배포 승인지침 문서가 저장소에서 바로 확인되지 않음
- 프런트 구조 리스크
  - `index.html` 단일 대형 파일 중심이라, 오픈 직전 대형 수정은 회귀 확률이 높음

## 3. 오픈 blocker를 다시 분류하면

상업 오픈을 막는 blocker는 아래 3층으로 보는 게 맞다.

### Blocker A — 바로 잠가야 하는 것들 (Stop-Ship)
이 중 하나라도 남아 있으면 외부 유료/대규모 유입 오픈 금지.

- 테스트용 관리자 접근 흔적이 운영 경로에 남아 있음
- 테스트 런처 기반 외부 공개 흐름 유지
- 관리자 시크릿 발급/회수/교체 절차 없음
- 운영 배포 절차가 "로컬에서 직접 띄우기" 수준에 머무름
- 백업/복구/롤백 절차 미정
- 오픈 전 회귀 검증 세트 부재

### Blocker B — 돈과 신뢰를 깨는 것들
코드 결함이 아니라도 상업 전환을 망칠 수 있는 항목.

- 결제/보상/구매/정산/자산 이전 동선의 릴리즈 전 반복 검증 미흡
- 관리자 패널 일부 탭/운영 도구의 재회귀 가능성
- 캠페인/영토/상점/인벤토리 등 장시간 플레이 동선에서 누적 오류 미검증
- 모바일/텔레그램/데스크탑 진입 UX 불일치

### Blocker C — 출시 후 CS 폭발을 만드는 것들
즉시 보안사고는 아니지만 상용 런칭 품질을 무너뜨린다.

- 혼합 언어 / 더미 문구 / 개발자 톤 노출
- 용어 불일치 (충전/보상/교환/점령/하이잭/조선/재료)
- 패치노트/점검공지/장애공지 템플릿 부재
- 버그 제보 채널 / 운영 응답 규칙 미정

## 4. 지금 당장 해야 할 실행순서

아래 순서는 "중요한 것"이 아니라 **실제로 이 순서로 해야 리스크가 줄어드는 순서**다.

## Step 0 — 출시 모드 선언 (오늘 바로)
목표: 기능개발 브랜치가 아니라 출시 안정화 브랜치로 전환

실행:
1. `commercial-open` 또는 이에 준하는 출시 안정화 브랜치 분리
2. 신규 기능 추가 중단
3. blocker 보드 생성
   - 카테고리: Security / Ops / Regression / UX / Localization / Launch Ops
4. 오픈 범위 확정
   - 이번 오픈에 **포함할 기능**
   - 숨길 기능
   - 관리자 전용 유지 기능
   - 실험 기능

완료 기준:
- "이번 오픈에 켤 기능/끄는 기능" 목록이 문서로 존재
- 기능 추가보다 blocker 제거가 우선이라는 합의 완료

## Step 1 — 테스트 공개 경로 제거 (최우선, Stop-Ship)
목표: 테스트용 운영 습관을 상업 릴리즈 경로에서 분리

실행:
1. `start-test.sh`를 상업 배포 경로에서 완전히 제외
2. 아래 항목 전수 점검
   - 기본 관리자 비밀번호
   - 하드코딩 시크릿
   - Cloudflare Tunnel 즉시공개 경로
   - 로컬 전용 편의 플로우
3. 운영 관리자 인증 정책 확정
   - 시크릿 저장 위치
   - 교체 주기
   - 유출 시 즉시 회수 절차
   - 운영자 접근 가능한 호스트/네트워크 범위
4. 테스트용 admin 접근 흔적을 오픈용 문서/스크립트/안내문에서 제거

완료 기준:
- "admin1234" 같은 기본값이 상업 경로에서 0건
- 외부 공개가 테스트 터널 의존이 아님
- 관리자 접근/시크릿 회수 절차 문서 1개 이상 존재

## Step 2 — 운영 기본선 만들기 (보안보다 먼저 필요한 운영 통제)
목표: 장애가 나도 감지/복구 가능하게 만들기

실행:
1. 운영 환경변수 명세 작성
   - 필수 env
   - 선택 env
   - 잘못 비었을 때의 장애 영향
2. health 기준 정의
   - HTTP 응답
   - DB 연결
   - WebSocket 생존
   - 마이그레이션 실패 시 시작 차단 여부
3. 백업/복구 기준 확정
   - DB 백업 주기
   - 복구 테스트 담당자
   - 복구 소요 목표시간
4. 배포/롤백 순서 문서화
   - 배포 전 체크
   - 배포 중 확인 포인트
   - 배포 후 스모크 테스트
   - 실패 시 롤백 조건
5. 장애 연락/공지 체계 확정

완료 기준:
- 운영자 1명이 아닌 **다른 사람도 따라 할 수 있는** 배포/복구 문서 존재
- "죽었는지 모르는 상태"를 막는 health 기준 존재
- 최소 1회 복구 리허설 완료

## Step 3 — 회귀 검증 팩 만들기 (현재 가장 중요한 실무 과제)
목표: 최근 감사 수정분이 다시 깨지지 않게 오픈 게이트를 만든다

실행:
1. 최근 수정 이력 기반으로 우선순위 높은 회귀 팩 정의
   - 관리자 로그인/후반 탭 접근
   - campaign editor auth
   - 회원/인증
   - 구매/보상/자원 차감
   - 영토 점령/방어/하이잭/수확
   - 함선 건조/함대 배치/인벤토리
2. 테스트 레벨 3단 분리
   - L1: 배포 직후 10분 스모크
   - L2: 오픈 전 1시간 핵심 경제/권한 리허설
   - L3: 주간 회귀팩
3. 자동화가 바로 어렵다면 최소 반자동 체크리스트부터 작성
4. 각 테스트 항목에 pass/fail 스크린샷 또는 로그 증빙 규칙 부여

완료 기준:
- "출시 전 반드시 돌리는" 체크리스트가 존재
- 관리자/경제/영토/상점 핵심 동선은 최소 1회 반복 검증 가능
- 최근 HIGH 회귀 포인트가 전부 체크리스트에 포함

## Step 4 — 상업 UX/문구 정리
목표: 실제 돈과 시간을 쓰는 유저가 이해할 수 있는 서비스 언어로 정리

실행:
1. 첫 30분 핵심 동선 문구 수집
   - 가입/로그인
   - 첫 보상
   - 상점/인벤토리
   - 영토 획득/점령/방어
   - 재화 사용/획득
   - 관리자 개입 가능 시스템 주변 안내
2. 용어집 확정
   - GP / PP / 재료 / 청사진 / 점령 / 하이잭 / 수확 / 업그레이드 등
3. 제거 대상 수집
   - 더미 문구
   - 혼합 언어
   - 개발자용 설명
   - 과도한 Web3 직설 문구
4. 모바일/텔레그램 진입 기준으로 문장 길이와 버튼 레이블 재검수

완료 기준:
- 핵심 결제/보상/영토 용어가 문서 1개로 통일
- 사용자 노출 더미/개발자 문구 제거 리스트 완성
- 첫 세션 UX에서 막히는 포인트가 0~소수로 줄어듦

## Step 5 — 소프트 오픈 리허설
목표: 정식 오픈 전에 작은 트래픽/작은 운영 인력으로 운영 가능한지 확인

실행:
1. 내부/지인 대상 폐쇄 리허설
2. 새 계정 기준 첫 세션부터 1시간 플레이
3. 운영자 기준
   - 유저 상태 확인
   - 보상 조정
   - 장애 확인
   - 공지 발행
   - 긴급 중지
4. 장애 시나리오 리허설
   - admin 탭 일부 실패
   - 결제/보상 오작동
   - 서버 재기동
   - DB 복구 필요 상황 가정

완료 기준:
- blocker 0개
- 운영팀이 오픈데이 런북만 보고 대응 가능
- 리허설 결과가 문서로 남아 있음

---

## 5. 출시 전 체크 게이트 — 더 날카롭게 다시 정의

기존 5개 게이트를 "통과 기준이 모호한 상태"에서 "실패하면 바로 오픈 보류되는 기준"으로 재정의한다.

## Gate 1 — Stop-Ship Security Gate
**질문:** 테스트용 접근/운영 구멍이 완전히 제거됐는가?

필수 통과 기준:
- 테스트 런처 기반 외부 공개를 사용하지 않음
- 기본 관리자 비밀번호/하드코딩 시크릿 노출 0건
- 관리자 인증 방식이 현재 문서화되어 있고 회수 절차가 있음
- 오픈 빌드에서 불필요한 관리자/실험 기능이 숨김 또는 차단됨

하나라도 실패하면:
- **정식 오픈 보류**

## Gate 2 — Economy & Permission Regression Gate
**질문:** 돈/자산/권한 관련 최근 수정분이 다시 안 깨지는가?

필수 통과 기준:
- 관리자 로그인 및 주요 후반 탭 접근 정상
- campaign/admin 계열 보호 엔드포인트 auth 정상
- 회원/로그인/비밀번호/삭제 흐름 정상
- 구매/보상/차감/정산/보상 수령 흐름 정상
- 영토/하이잭/수확/업그레이드 흐름 정상
- 최근 HIGH/CRITICAL 수정 영역 회귀팩 100% 통과

하나라도 실패하면:
- **유료 오픈 보류**

## Gate 3 — Launch Ops Gate
**질문:** 장애가 나면 누가 어떻게 감지하고 되돌리는가가 명확한가?

필수 통과 기준:
- 배포 문서 있음
- 롤백 문서 있음
- 백업/복구 문서 있음
- health 기준과 확인 방법 있음
- 운영자 연락/공지/점검 템플릿 있음

하나라도 실패하면:
- **대규모 외부 유입 오픈 보류**

## Gate 4 — Commercial UX / Localization Gate
**질문:** 일반 유저가 서비스 의도를 오해하지 않고 플레이 가능한가?

필수 통과 기준:
- 첫 세션 핵심 동선 막힘 없음
- 결제/보상/점령/인벤토리 용어 통일
- KO/EN/JA/ZH 주요 노출 문구 점검 완료
- 더미/혼합언어/개발자 문구 제거 완료
- 텔레그램/모바일 기준 버튼/배너/오류문구 QA 완료

하나라도 실패하면:
- **마케팅 유입 확대 금지**

## Gate 5 — Launch Rehearsal Gate
**질문:** 오픈 당일 운영을 실제로 해봤는가?

필수 통과 기준:

## 6. 추천 릴리즈 전략

지금 상태에서 맞는 전략은 "한 번에 정식 상업 오픈"이 아니라 **3단계 오픈**이다.

### Release Stage 1 — Private Stabilization
대상:
- 내부/지인/소수 검증 그룹

목표:
- 운영 경로 분리
- 회귀 검증 팩 고정
- admin/경제/영토 핵심 흐름 안정화

오픈 조건:
- Gate 1 일부 통과 + Gate 2 최소 스모크 확보

### Release Stage 2 — Soft Commercial Open
대상:
- 제한된 외부 유입
- 소규모 과금/잔존 데이터 관찰

목표:
- CS 패턴 수집
- 경제 흐름 이상치 확인
- 운영자 실제 대응 속도 검증

오픈 조건:
- Gate 1~4 통과
- Gate 5 리허설 1회 완료

### Release Stage 3 — Full Commercial Open
대상:
- 마케팅/확장 유입

목표:
- 안정적 운영
- 공지/점검/핫픽스 루틴 고정

오픈 조건:
- Gate 1~5 모두 통과
- blocker 0
- 롤백 플랜 검증 완료

## 8. 최종 판단

현재 `occupy-mars`는 **코드 기능 부족 때문에 못 여는 상태는 아니다.**  
하지만 아직 **"상업 운영 습관"이 코드 안정화 속도를 따라오지 못하는 상태**다.

따라서 오픈 준비의 핵심은 다음 한 줄로 정리된다.

**"새 기능을 더 넣는 것"이 아니라, 테스트용 공개 경로를 제거하고, 최근 감사 수정분이 다시 깨지지 않도록 운영 게이트와 회귀 게이트를 먼저 세우는 것.**

이 문서 기준으로 움직이면, 지금 가장 현실적인 오픈 blocker는 다음 3개다.

1. **테스트 런처/기본 관리자 접근 흔적 제거**
2. **배포 전 회귀 검증 팩 구축**
3. **배포/백업/롤백/장애대응 운영 런북 확정**

이 3개가 정리되기 전에는 정식 상업 오픈보다 **제한적 소프트 오픈**이 맞다.
