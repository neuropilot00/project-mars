# 전투 화면 연속성 검증 — 2026-10-30

## 느린 클라이언트

상태 프레임이 처리 속도보다 빨리 오면 묵은 프레임을 무제한 보관하지 않고 실제 포격 판정을 진영·무기별 수량과 실제 대표 궤적으로 합산한다. 선택적 gzip-v2의 표시 요약으로 압축을 풀기 전 병합할 수 있다. 정상 프레임 적용 후 서명된 커서를 확인 응답하며 명령·종료 순서는 보존한다. 같은 프레임 재전송은 중복 집계하지 않는다. 포격 표시 자리가 꽉 찰 때도 요약을 이월하고 새 전투 또는 리플레이 탐색 시 오래된 이펙트는 제거한다. 모든 탄환을 개별 선으로 무한히 재생하는 것은 아니며 피해·보상은 서버가 결정한다.

요약의 크기·좌표·수량 제한과 우발적 손상 검사는 적용한다. 비밀 없는 체크섬은 위조를 막는 인증이 아니며, 화면 데이터는 WSS와 서버를 신뢰한다. 서버가 발행한 복구 cursor는 HMAC으로 검증한다. 구형 서버/클라이언트는 기존 wire 형식을 유지한다.

## Redis 재연결의 보장 범위

전투 권위 프로세스가 살아 있으면, 화면 적용 지점의 서명 cursor와 진영·무기별 누적 판정으로 Redis 중단 구간을 bounded 상태에서 복구한다. 최근 128프레임을 넘어도 해당 실행 epoch의 누적 count와 실제 대표 좌표를 이용한다. 최신 서버 HP와 종료 결과를 복원하며 다른 소유자의 명령 응답은 전달하지 않는다. 명령을 전달할 권위 경로가 없거나 복구 중이면 지휘 요청을 명시 거부한다. 접수 후 적용 결과가 9초 안에 오지 않으면 자동 재전송하지 않고 확인 불가를 표시하며, 늦은 실제 결과는 반영한다. 사전계산 재생의 관전자 없는 중단 구간도 요약을 보존한다.

**한계: Redis 장애로 스케줄러 리더 락이 소실되어 프로세스가 종료되면 진행 중 전투 상태는 현재 메모리에 있어 이어서 실행하지 못한다.** 격리 Redis를 32초 중단한 실제 leader.js+엔진 재현에서 프로세스가 종료됐다. 안전한 자동 인계에는 실행권 fencing, 내구성 있는 전투 checkpoint, 명령 ID 중복 방지 및 적용 ACK의 원자성, 보상·길드 후속 처리의 idempotent outbox와 장기 용량 검증이 필요하다. 결제·재화 중복 방지를 위해 리더 보호를 완화하지 않았다. PostgreSQL의 승인된 1000MB 볼륨을 증설하거나 데이터를 지우지 않았다.

## 검증

- 로컬 Chrome 320/390, 600개 프레임을 10ms 간격으로 밀고 각 처리를 25ms 인위 지연: 상태 프레임은 합쳐졌으나 13,200/13,200 판정, 양 진영, 명령 ACK, 최종 적용 cursor를 보존했다. 실제 기기/WAN은 아니다.
- 두 독립 WS 프로세스와 로컬 Redis, 200개 합성 연결, 실제 엔진 기반 552척 상태 프레임, Redis 중단·128프레임 범위 초과·복구: 양 진영 누락 집계·최신 HP·종료 1회와 다른 소유자 명령 응답 비노출을 확인했다. DB/인증은 fixture이며 실제 leader 종료 시나리오는 포함하지 않는다.
- 리더 보호는 그대로 유지했으며 기존 전투/재화 데이터를 수정하거나 백필하지 않았다. 후속 길드전 승점 처리에서 draw가 방어 승리로 간주되던 기존 버그를 수정했다.
